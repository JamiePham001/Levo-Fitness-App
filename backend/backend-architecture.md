# Backend Architecture

ASP.NET Core (.NET 10) minimal API, EF Core + Npgsql on Postgres (Supabase in production, local Postgres in dev), Supabase Auth for identity. Deployed serverless (API Gateway + Lambda). Code is organised as vertical slices under `Features/`; shared infrastructure lives in `Database/`.

## Auth and identity

- Supabase Auth owns credentials and sign-in (Google and Apple OAuth). It keeps its own users in the `auth` schema; our `Users` table is a profile table.
- `User.Id` is the Supabase `auth.users.id`, the JWT `sub` claim. It is generated by Supabase, never by the client or this backend, and the JWT signature is what makes it trustworthy.
- The backend validates the JWT on every request (signature via Supabase JWKS, issuer `https://<project>.supabase.co/auth/v1`, audience `authenticated`, expiry).
- ASP.NET may remap `sub` to `ClaimTypes.NameIdentifier`; set `MapInboundClaims = false` or read the mapped claim.
- Signup: client signs in with Google/Apple, prompts for a unique username, then `POST`s the username with the JWT in the `Authorization: Bearer` header. The backend takes `id`, `email`, provider (`app_metadata.provider`) and avatar (`user_metadata.avatar_url`, may be missing for Apple) from the token and the username from the body. Username uniqueness is enforced by the unique index; a violation returns 409.
- The owner of any row is always the JWT `sub`, never a value from the request body.
- Until the profile row exists, other endpoints must return a distinct "profile incomplete" response so the client can send the user back to the username step.
- Configuration lives in user secrets locally (read only when `ASPNETCORE_ENVIRONMENT=Development`, which `launchSettings.json` sets; `dotnet run --no-launch-profile` runs as Production and sees none of them):
  - `SupaBase:ConnectionString`: a `postgresql://` URI or an Npgsql keyword string. URIs are converted by `PostgresConnectionString.Normalize` (SSL required).
  - `SupaBase:ValidIssuers`: `https://<project>.supabase.co/auth/v1`, comma-separated for several. The setting may instead hold the full JWKS address (`.../auth/v1/.well-known/jwks.json`): `SupabaseAuth.ParseIssuers` strips that suffix and any trailing slash, because the issuer in a token is the part before `/.well-known`. The first issuer also locates the signing keys.
- Token validation is `AddSupabaseAuth` in `Features/Auth`. The project signs with an asymmetric key (ES256, P-256), so no secret is stored: the public keys are downloaded from `<issuer>/.well-known/jwks.json`, cached for an hour, and refreshed when a token names an unknown key, so key rotation needs no change here. Only ES256 is accepted (blocking `none` and HS256 algorithm-confusion tokens), and signature, issuer, audience `authenticated` and lifetime (no clock skew) are all required. `MapInboundClaims` is off so the user id is the `sub` claim.
- The `x` and `y` values on Supabase's JWT Signing Keys page are the public key coordinates and are not secrets or HMAC keys; they are not used here because the JWKS endpoint serves the same key.
- Supabase's direct connection host (`db.<ref>.supabase.co`) is IPv6-only. From IPv4-only networks, and from AWS Lambda unless it is set up for IPv6, use the pooler connection string (`aws-0-<region>.pooler.supabase.com`, user `postgres.<ref>`; port 5432 session mode or 6543 transaction mode).

## Data model

- `SyncEntity` (base class) carries the sync fields: `ClientUpdateAt` (device clock, clamped), `ServerUpdateAt` (server-stamped), `DeletedAt` (tombstone), `UpdatedByDeviceId`. All have private setters. Only `BeginSync(clientUpdateAt, deletedAt, deviceId, now)` writes them: it rejects an empty device id or missing timestamp, clamps a future client timestamp to `now + 5 min`, normalises to UTC, applies last-write-wins, and sets the tombstone. Entities never assign sync fields themselves, so none can forget the tombstone.
- `Guard` holds shared validation. Text is trimmed and length-checked against the column, numbers must be finite (NaN and infinity pass a plain `> 0` check), and enums are checked with `Enum.IsDefined`, never `== default`, because the default value is a valid member.
- Enums are stored as strings. All timestamps are `timestamptz` and must be UTC. `Username` and `Email` are `citext` (case-insensitive); the `citext` extension is created by the migration.
- Indexes on every synced table: `(UserId, ServerUpdateAt)` for the pull, and a filtered `(UserId, DeletedAt) WHERE DeletedAt IS NOT NULL` for the tombstone purge.
- Namespaces are plural (`Goals`, `Users`, `Programs`, ...) while folders stay singular. A namespace named after its class (`Goal.Goal`) makes the bare type name ambiguous.
- The program entity is named `TrainingProgram` (table `Programs`) so it never collides with the compiler-generated top-level `Program` class, which integration tests need for `WebApplicationFactory<Program>`. Its DTO and enum keep the `Program` prefix (`ProgramSync`, `ProgramType`).

### Entities

Synced (`: SyncEntity`, client-generated `Id`, `UserId` owner, `Create` + whole-snapshot `ApplySync`):

| Entity | Parent | Notes |
|---|---|---|
| `User` | none | `Id` is the Supabase user id. A username has no whitespace or control characters; letters, digits and special characters are allowed, up to 30 characters, case-insensitively unique. Sync only touches `Gender`, `Weight`, `Measurement`. Username, email, provider, avatar and `Role` are server-owned, and sync can never tombstone a user. |
| `Goal` | none | |
| `Movement` | none | Only the user's custom movements; the built-in library lives on the client. Custom movements sync so they appear on every device. Keywords are trimmed, lower-cased, de-duplicated, max 20. |
| `TrainingProgram` | none | |
| `ProgramBlock` | `Program` | Name is optional. |
| `Workout` | `ProgramBlock` (optional) | `BlockId` is null for a workout outside any program. `Name` is optional and may be blank. `CreatedAt` is set by the device, clamped and normalised like other client times, and never changed by later syncs. |
| `Exercise` | `Workout` | `MovementId` is a soft reference (no foreign key) and `Name` is a snapshot, so purging a movement tombstone never breaks exercise history. |
| `ExerciseSet` | `Exercise` | `Order` sequences sets. Weight, reps and RIR are nullable for planned sets. RIR is 0 to 10 and rest time 0 to 3600 seconds. |

A parent id is fixed when the record is created. `ApplySync` throws if a snapshot names a different parent.

Online-only (not synced, created through ordinary endpoints, `Create(..., now)`, server-generated ids):

- `Friendship`: only the receiver can `Accept` a pending request; either participant can `Block`; the blocker is recorded in `BlockedById`. Cancel, decline, unfriend and unblock all delete the row, and `CanRemove(actorId)` says whether a caller may (a block can only be lifted by the blocker). A friendship is unique per pair in either direction (expression index `UX_Friendships_Pair` on `LEAST/GREATEST`, created by raw SQL in the migration).
- `ProgramShare`: `ShareAccess` is `Download` or `Collab`. Unique per `(ProgramId, ReceiverId)`. Revoking deletes the row. Only `Download` is in scope: the receiver copies the program into their own account. `Collab` is reserved for a possible future feature and has no behaviour.
- `Notification`: an inbox pointer (`ReceiverId`, `SenderId`, `Type`, `TargetId`, `ReadAt`). State lives on the target. Unique per `(ReceiverId, Type, TargetId)` so a retried request cannot duplicate it. Read notifications older than 30 days are deleted when the receiver fetches their inbox.

### Rules the sync handler must enforce

These are not expressible in the entities:

- **Parent ownership.** Before creating a child (block, workout, exercise, set), check that the parent row exists and `parent.UserId == sub`. Foreign keys only prove the parent exists, so without this a client could attach records to another user's parent.
- **Tombstone cascade.** The client must tombstone children together with their parent. A purge hard-deletes an expired parent and the database cascades to its children, so any child without its own tombstone would disappear without other devices ever learning of it.
- **Apple and OAuth profile gaps.** Apple may withhold name and email. Do not rely on the provider for a username.

## Sync

The client is offline-first (SQLite). All synced data is private to one user. Synced data goes through a single endpoint, `POST /sync`, in a `Features/Sync` slice. Server-owned things (profile and username, role and premium status, Stripe webhooks, username availability, AI calls) use ordinary endpoints. Supabase Realtime only nudges the client to call `/sync`; it carries no data.

### Request and response

```
POST /sync   (Features/Sync)
{ deviceId, cursor, changes: { user, goals, movements, programs, blocks, workouts, exercises, sets } }

-> { cursor, hasMore, fullResyncRequired,
     results: { user, goals, ..., sets },     // what happened to each record the client sent
     changes: { user, goals, ..., sets } }    // what changed on the server since the cursor
```

Every list in `changes` is optional on the way in. The response always has every list (empty when nothing changed), and `user` is null when the profile did not change. Pushed and pulled records use the same `*Sync` types, and the server builds the pulled ones with each entity's `ToSync()`.

The code is split by direction: `SyncPush` applies what the client sent, `SyncPull` builds what comes back, `SyncCursor` owns the bookmark, and `Sync` holds the endpoint and the contract types.

### Per-record results

Each record the client sends is judged on its own and appears in exactly one list of its table's result: `{ applied: [ids], rejected: [{ id, reason, message, serverVersion }] }`. One bad record never stops the others, and the applied ones are saved together in one `SaveChanges`.

| reason | meaning | `serverVersion` |
|---|---|---|
| `stale` | the server already holds a snapshot at least as new (this is also what a re-sent, already applied record reports) | the server's record, so the client can replace its losing copy |
| `invalid` | the record failed validation, including a missing `ClientUpdateAt` and an attempt to move a record to another parent | none |
| `notOwner` | the id belongs to another user; the row is never touched | none |
| `parentNotFound` | the parent is missing or not the user's (same reason and message for both) | none |
| `notFound` | the profile row does not exist yet (the `user` record only) | none |

Entities validate before they change, so a rejected record leaves no trace. A rejected record is the client's to fix or drop; a `stale` one is answered by `serverVersion`.

Status codes for the request as a whole: 401 without a valid token, 400 for a missing device id or a bad or future cursor, 200 otherwise (including when some or all records were rejected).

### The cursor

The cursor is the server's bookmark for what a device has already received. It is an opaque string to clients: store the one from each response and send it back (`null` on a first sync). Today it is the UTC tick count of the moment the last pull started minus 10 seconds. The overlap catches rows from a transaction that was stamped before, but committed after, the previous pull; clients apply pulled rows idempotently, so a repeat is harmless. The server rejects a cursor that is unparsable or in the future, and answers `fullResyncRequired` (applying nothing) when it is older than 90 days, since tombstones older than that may have been purged. A request without a cursor is a first sync and pulls everything.

`GoalSync` is a full snapshot of the client-owned fields plus `ClientUpdateAt` and `DeletedAt`. Creates, updates and deletes are all the same shape; a delete is a snapshot with `DeletedAt` set.

### Server flow

1. **Authenticate.** `userId` = JWT `sub`.
2. **Stale-device check.** If `lastPulledAt` is older than the 90 day retention window, return `fullResyncRequired` and apply nothing. The client wipes local data and pulls everything. A first sync (no cursor) is a full pull.
3. **Push (apply).** For each synced entity type:
   - Dedupe incoming records by `Id` (keep the newest `ClientUpdateAt`).
   - Load the existing rows for the incoming ids in one query, keyed by `Id` only (not filtered by `UserId`). Index them in a dictionary.
   - For each incoming record:
     - No existing row: `Goal.Create(userId, dto, deviceId, now)` and add it.
     - Existing row owned by another user: reject as not owner. Filtering the load by `UserId` would hide the row and make the insert collide on the primary key.
     - Existing row owned by this user: `existing.ApplySync(dto, deviceId, now)`. `false` means the snapshot was stale, so reject it and return the server's version. Throwing `ArgumentException` means invalid, so reject it with a reason.
   - One `SaveChanges` and one transaction for the push. Results are per record, not all-or-nothing; applies are idempotent, so retries are safe.
   - `ApplySync` overwrites every client-owned field in one call and validates once. It never touches `Id`, `UserId` or `ServerUpdateAt` from the payload.
4. **Pull.** After the push is saved, return rows for `userId` where `ServerUpdateAt > lastPulledAt - overlap`, excluding rows whose `UpdatedByDeviceId` is the caller's device (echo suppression), ordered by `ServerUpdateAt`, paged. Tombstoned rows are included. `hasMore` tells the client to call again; the cursor only advances to the last row returned.
5. **Purge.** Hard-delete the caller's tombstones older than 90 days (by `ServerUpdateAt`), with `ExecuteDeleteAsync`, after the push and pull are done.

### Resolved decisions

- **Single endpoint, push then pull.** Push first so the pull reflects the merged state.
- **Whole-object updates.** Sync paths use whole-snapshot `ApplySync`, not per-property methods. The online API can keep small intent-named methods.
- **Conflicts: last-write-wins on `ClientUpdateAt`.** A snapshot not strictly newer than the stored one is rejected and the server's version is returned. `ClientUpdateAt` is **clamped** to `now + a few minutes` before applying, so a device with a clock in the future cannot win every conflict.
- **Cursor is server time.** The client stores `cursor` as `lastPulledAt`. Client clocks are never used for pulling. The pull subtracts a small overlap (5 to 10 seconds) so rows committed late by a slow transaction are not missed; the client applies pulled rows idempotently.
- **Rejected records return the server version.** The winning row may be older than the cursor, so it would not appear in the pull.
- **Echo suppression** uses `UpdatedByDeviceId`. A rejected stale push does not change it, so the winner's device still receives the row.
- **Tombstones are kept for 90 days.** The server must not delete a row at once, because a second device that has not synced would never learn of the delete and could resurrect the row by editing it. Tombstones are pulled like any other change. The client deletes its local copy when it sees one (and may purge its own local tombstone as soon as the server acknowledges the push). Deleting a row that is already gone is treated as success.
- **Purge on sync, not cron.** Each sync purges the caller's expired tombstones. Retention age uses `ServerUpdateAt`, not the client-supplied `DeletedAt`. Tombstones of users who stop syncing stay in the table.
- **Limits.** API Gateway allows 10 MB and 29 s per request and Lambda 6 MB for the body, so the push batch size is capped and the pull is paged.
- **UTC only.** Incoming timestamps are normalised to UTC before use; Npgsql rejects non-UTC `DateTime` for `timestamptz`.

### Status

Done: `Create` / `ApplySync` / `ToSync` for every synced entity, the online-only entities, the DbContext and its migrations, JWT validation, and the `POST /sync` endpoint (apply with per-record results, ownership and parent checks, pull, cursor, stale-device check) with unit and in-memory integration tests.

Not yet built: paging (`hasMore` is always false), the tombstone purge, the online endpoints (friends, shares, notifications, profile creation), and integration tests against a real Postgres. Clamping and normalisation of client timestamps are not applied: `SyncEntity.BeginSync` stores device times as sent (it only rejects a missing one). The in-memory provider does not enforce foreign keys, unique indexes or `citext`, so those are untested. A user without a profile row cannot save any synced records against a real database (the foreign key to `Users`); profile creation at signup has to come first.

## Database

- `Database/AppDbContext.cs` maps `User` and `Goal`. `Friendship` has no fields yet and is not mapped.
- Migrations live in `Database/Migrations` and are marked generated in `.editorconfig` so analyzers skip them.
- Create a migration (a throwaway connection string is enough, no database connection is made):
  `ConnectionStrings__Default="Host=localhost;Database=x" dotnet ef migrations add <Name> -o Database/Migrations`
- Apply to the local database: `dotnet ef database update` (needs the user secret set).
